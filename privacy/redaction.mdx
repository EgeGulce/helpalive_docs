Every event flows through two redaction layers before it reaches durable storage. This page details what each layer strips, what's never captured at all, and what the guarantees mean for your users.

## Never captured

Some fields are never observed by the SDK in the first place:

- **Keystroke contents.** The SDK doesn't watch keys typed into inputs (we only react to keyboard shortcuts, never to character data).
- **Form input values.** Submit events fire when a form is submitted; the values inside the inputs do not flow.
- **Password fields.** Excluded fully — never captured, never transmitted, no hashing.
- **Anything you mark as private.** Add `data-helpalive-redact` to any element you want kept out of selectors and exposure data — useful for sensitive labels (account numbers, balances).

## Layer 1 — in the browser

Before any payload is sent, the SDK runs:

### URL hygiene

URLs are normalized before transmission. Anything in the path, query, or fragment that looks like personal data is replaced.

| Original | After hygiene |
|----------|---------------|
| `/users/jdoe@example.com/edit` | `/users/:redacted:/edit` |
| `/billing?email=jdoe@example.com` | `/billing` |
| `/share#token=eyJhbGc...` | `/share` |
| `/orders/4827` | `/orders/4827` *(numeric IDs preserved — not PII)* |

### Pattern stripping

Captured text passes through pattern-based redaction:

| Pattern | What's stripped |
|---------|-----------------|
| Email | `jdoe@example.com` → `[email]` |
| Phone | `+1 415 555 0123` → `[phone]` |
| Card number | `4111 1111 1111 1111` → `[card]` |
| US Social Security number | `123-45-6789` → `[ssn]` |
| IPv4 | `203.0.113.7` → `[ip]` |

### Anonymous element identifiers

When the SDK records that a user clicked something, it doesn't send the element's class names, IDs, or text content. It sends an anonymous identifier that's stable for analytics grouping but reveals nothing about what the element actually says.

### Fail closed

If the redaction layer ever throws (it shouldn't — but software), the batch is dropped, not transmitted. Better lost analytics than leaked data.

## Layer 2 — on our servers

After the browser pass, events arrive at a private intake process. We apply a heavier pass that catches things the browser layer can't reasonably handle:

- Names and addresses (which need a language model to recognize, not a regex).
- Locale-specific identifiers (national IDs, regional phone formats, address shapes).
- Edge cases in punctuation, formatting, or context that pattern matchers miss.

Detected entities are replaced with type tokens (`<PERSON>`, `<EMAIL_ADDRESS>`, `<US_SSN>`) before storage.

### Why two layers?

The browser pass is fast and catches the obvious patterns. The server pass is comprehensive — it uses industry-standard PII detection that's far more thorough than what we can ship into a small browser SDK. Together, they cover the cases each one alone would miss.

### Isolation

The intake process is the **only** part of our infrastructure with access to raw event data. The dashboard never sees raw events — only the redacted output. This is enforced by infrastructure, not by policy.

## Storage layout

| Store | What's in it | Redacted |
|-------|--------------|----------|
| **Event analytics** | Long-term redacted events | Yes — both layers |
| **Chat conversations** | Question and answer text | Yes — server-side pass |
| **User profiles** | Identity and traits you sent (display name, email, plan) | Stored as you sent them |

## Where verbatim text intentionally survives

Two places intentionally keep verbatim user input:

1. **Chat conversations** (after PII redaction). The whole point of the chatbot is to read user questions and respond, and the whole point of [Coverage gaps](/analytics/coverage-gaps) is to surface what users ask. Personal data is stripped, but the question is otherwise kept.
2. **Identity fields** (`displayName`, `email`). You provide them through `identify()`. They live on the user profile so admins can search and support, scoped per customer and removable on DSAR request.

## Audit

Every redaction pass logs:

- Counts of detected entity types per minute (no payloads).
- Internal queue depth and lag.
- Failed redaction attempts (rare; alerts on threshold).

These are visible internally for HelpAlive operations; they aren't currently exposed to customer dashboards.
